## 1. 结论与比较目标

采用“**完整旧 test 回归＋1,200 个新增复核窗口的主比较＋重复性能／显存测试**”。新增集目标约 6,000 条计分字幕，四候选共约 24,000 条翻译；旧 test 的 83 窗口／414 条另报。不能仅完成 smoke 或旧 test 就宣称这轮大规模比较完成，也不能把同一窗口重复运行算成新质量样本。

回答三个问题：

1. 新量化是否减少错意、漏译和严重错误，收益能否跨作品保持，而非只提高一点裁判均分？
2. 在当前 5080 和冻结配方下，能否持续运行；是否发生加载／推理 OOM、部分 offload、共享内存增长或异常降速？
3. 若质量接近，哪个版本的吞吐、延迟、显存余量、稳定性和维护成本更合适？无法稳定区分时继续保留现基线。

1,200 是本轮工程规模目标，不是证明小差异必然可检出的功效保证。仅 15 个作品、其中 4 部电影，增加同作品片段不能消除作品相关性和同模型裁判偏差。

## 4. 数据规模与扩集方法

| 分轨 | 每候选规模 | 用途与计分边界 |
| --- | ---: | --- |
| 现有 smoke／dev | smoke 15／75；完整 dev 41／204 | 接口、容量、裁判与配方验证；smoke 属于 dev，不重复计分 |
| 历史回归 | test 83 窗口／414 条 | 全量运行并同轮重评，单独报告；已经用于选型，标为 test-informed 回归 |
| 新增主比较集 | 目标 1,200 窗口／约 6,000 条 | 每作品 80 个新窗口，11 剧集＋4 电影；全部复核后冻结并全量评估 |
| 容量压力集 | 固定 dev／合成探针 | 最长输入、最大合法输出预算、连续运行和重新加载；只评工程稳定性 |

新集从现有清洗候选及源事件映射扩展，保留既有 15 作品范围。库目录记录有 342 集候选；数量不代表质量已审核或每集均可纳入。具体步骤如下：

1. **先定源清单，再看候选模型输出。** 剧集每作优先选择 8 个未被现有 dev/test 使用的集数，每集 10 个窗口；按季／集段分层后用 seed `20261006` 确定性抽样。电影每作取 80 个窗口，按对白进度十等分，每层目标 8 个。保留抽样框、随机顺序、纳入概率和拒绝原因。
2. 沿用通常 7 个源单元／中间 5 个计分的窗口契约；真实计分 ID 数由清单决定。窗口的全部 context 源事件相互不重叠，也不与旧 dev/test 重叠；不通过平移一个句子制造多个“独立”样本。剧集尽量分散集数，不让单集主导一部作品。
3. 依据原日文和既有中文候选进行双轮 `gpt-6.1-sol / high` 文本复核，第二轮使用 fresh 请求，先独立判断；必要时有界裁决。参考建设人员不看四模型输出、身份或评分。保留原译文、修改理由、源映射和排除记录；只修改确定错误，不统一合理措辞。
4. 无法在最终提供的日文上下文中判定、日文源损坏、对齐不可确认或需音画才能确认的窗口隔离。按事前冻结的同层候补顺序补足；补样不能依据某模型输赢。天气之子保持隔离，不为凑数量恢复纳入。
5. 为降低额外筛选偏差，记录各作品、位置层的初始样本数、拒绝率和最终数量；质量结论限定为审核后可用场景。源侧标注省略／指代、否定／条件、专名、数字、口语、长句等诊断标签，不按候选表现改变抽样。风险标签只做切片分析，不挤占概率抽样主集。
6. 在仓库忽略目录创建独立语料版本，例如 `.local/translation-evaluation/<run-id>/corpus/hy30-expanded-v1/`；模型输入和参考分目录，manifest 冻结所有文件及构建脚本。原 v2 不改。新窗口 ID、作品／集数／源事件和时间范围可追溯，扩集构建与参考审核日志齐全。
7. 若某作品不足 80 个合格、不重叠窗口，先从同作品更多可用剧集／片段补足；电影不可凭空扩充。公布实际短缺及原因，在看到模型成绩前冻结修订规模。未达到目标须标为规模不足，不能合并旧 dev 或重复样本冒充完成。

新集使用 `V2-native-adapted` 的相同窗口契约与评估 schema，但必须声明新语料版本，不称其为原版 v2 test。旧 test、新集和 dev 不汇成一个“独立测试分数”。新集只保证本轮配方冻结后的片段留出，不声称未见作品、真人电影或跨系列泛化。

## 5. 统一推理配方与最小 demo 工作

优先以当前基线配方比较四者：temperature 0、seed 20261006、输出上限 1024、context 4096、batch 256、ubatch 128、单槽、flash attention on、fit off、GPU layers 99；`native-target-json-gbnf-v3`＋`token-ids-v1`、Hy30 `no_think`、fresh 窗口、`cache_prompt:false`，最多两次相同请求。保存停止 token、KV 类型、CPU 线程等实际完整设置，不依赖未记录默认值。

四者接收相同完整日文 context 和计分 IDs，不加入中文参考、历史判断、跨窗历史、额外背景或修补模型。输入加输出预留超预算时不得静默截断。全 GPU 是主轨目标，不静默降低层数、context 或输出预算。

已实现新增三款候选注册、两份资产清单合并校验、统一 runtime session worker、阶段资源监测、
缺失调度分母、恢复编排和配对统计；实际入口与字段见上述 demo／eval／judge 及
[串行比较说明](../../experiments/translation_four_quantization/README.md)。四款完整 smoke/dev 与稳定性任务已终结，
但工程终态不等于通过全部容量／质量门槛；具体成功、容量失败、缺测与冻结身份以接跑记录和原始产物为准。

资产核查保留 GGUF 架构、tokenizer、特殊 token、Jinja、bias 命名、量化类型分布和实际 offload；
同源 prompt／token 输入差异按资产身份披露。改动引擎或配方须四者统一回归，不能混入纯量化结论。
工程冻结可仅包含 smoke/dev；正式冻结仍必须匹配双轮参考复核后的新增语料、旧 test、源事件隔离及完整源码哈希。
正式冻结与工程身份不同，允许只读引用已验证旧 smoke/dev，但每候选仍需新 session 的预热与容量探针；
不得改写工程冻结或将其直接当作正式完成证据。

复用现有 demo／eval／judge，不另写四套独立翻译程序。实施后运行相关离线单测和四款完整 smoke/dev，覆盖未注册资产、重复身份、输入超限、OOM／退出、缺失窗口、裁判缺分和不等作品规模汇总；真实模型 smoke 与离线检查分别记证据。

## 6. 显存、OOM 与稳定性

每次只加载一个模型；记录 Windows、GPU UUID／实际总显存、驱动、引擎及 DLL 哈希、CPU/RAM、后台 GPU 占用。停止本实验自己的残留服务；不自行终止用户其他程序。加载前记录至少 30 秒空闲基线，卸载后验证本实验进程退出和显存释放。候选开始条件明显不同时标记污染，安排新独立轮次，保留原记录。

| 检查 | 采集与判定 |
| --- | --- |
| 加载／推理／卸载 | 全程时间戳、阶段标记、原始 stdout/stderr、退出码；区分分配 OOM、请求 OOM、超时、崩溃和接口错误 |
| GPU 驻留 | loader 的实际 offloaded／total 层数、GPU model buffer、KV 与 compute buffer；请求 99 层不等于已证明全驻留 |
| 显存曲线 | 目标 200–500 ms 采样 used/free/total，实测采样间隔与开销；不可用则降为 1 秒并披露漏峰风险。峰值是整卡采样峰值，非模型独占或绝对峰值 |
| Windows 内存 | 可用时记录目标进程 dedicated/shared GPU memory、working set／commit、系统 RAM；不可用写 null 及原因。CPU_Mapped buffer 不当作 CPU 实际驻留量 |
| 隐性降速 | 对齐 shared memory、RAM、GPU 利用率、功耗／温度／时钟与请求延迟。全层 offload 日志不能单独排除 Windows 内存迁移；只有慢不足以断言发生了迁移 |
| 余量与长跑 | 报告最低空闲显存、长跑前中后占用、p95/p99 延迟、后半段相对前半段速度；用相同输入块诊断持续增长，避免长度分布混杂 |

容量预检顺序：基线 → i1-Q3_K_M → APEX-I-Compact → i1-Q3_K_L；性能正式轮次另做平衡排序。短 smoke 通过后仍需完整主集、最长合法输入探针，以及各款至少一次 30 分钟连续请求稳定性测试。后者可循环同一固定输入，单列重复次数和负载，绝不计为新增质量样本。接近 4096 总预算的合成探针保留输出余量；8192 context 或更大并发属于另一个可选配方，不混入本轮主结论。

**OOM 处置**：立即留存失败证据并停止该进程的无效重复请求；清理仅本实验进程，确认内存回落后，同配方最多做一次诊断重试。重复 OOM 则该配方容量不通过，不无限重试。其余候选继续。若 OOM 发生在正式冻结后，失败请求与未执行尾段分别记账；不能把尾段伪造成全部实际翻译失败。

若需研究部分 offload 或更小 batch/context，单建“可运行配方”附录，先在 dev 明确固定策略再跑；不能静默救活后并入全 GPU 主表。无法全 GPU 的候选仍列在四候选总表中，保留容量失败与缺失质量证据。本计划不预先替用户选择牺牲速度的混合基线。

## 7. 正式运行与四模型翻译耗时对照

**翻译耗时是本轮必交付的核心指标，也是判断显存压力的旁证。** 最终报告必须并列四款模型在相同输入集上的耗时，不能只给 token/s 或笼统的性能描述。旧回归集与新增主集分别出表，每款至少包含以下字段：

| 必报字段 | 统一口径 |
| --- | --- |
| 完整集翻译墙钟耗时 | 从首个正式窗口开始到最后一个窗口终态落盘，包含 tokenization、请求、校验、重试及运行器开销；不含冷加载、预热、参考建设和裁判 |
| 相对基线耗时 | 四轮完整集耗时中位数之比、绝对多／少秒数与百分比；同时保留各轮值和范围 |
| 逐窗口延迟 | 请求总耗时的 p50/p95/p99、最大值，并列输入／输出 token 数；报告相同窗口相对基线的耗时比，定位突发长尾 |
| 启动与全流程耗时 | 冷进程加载、预热分别列出，另报加载到全部翻译结果落盘的端到端耗时 |
| 完成度与失败成本 | 已完成／预期窗口、成功／失败／未执行数量及重试耗时；未跑完的部分耗时不能当完整集更快的证据 |

逐窗开始／结束时间与显存、共享内存、GPU 利用率曲线使用同一时间基准，重点列出“显存接近上限时延迟突增”“共享内存增长伴随持续降速”“长跑后半程变慢”的关联证据。比较相同源窗并结合生成长度、温度／时钟、后台负载和实际 offload 状态解释差异。明确 OOM 错误才记为已发生 OOM；只有耗时异常时记为显存压力或迁移疑点，不单凭慢认定爆显存。不同量化内核、输出长度和热降频也可能造成速度差异。

完成资产、扩集与 dev 后冻结源码、输入／参考、四模型与引擎、模板、采样设置、裁判提示、统计规则和运行顺序；冻结后不得根据 test 分数调参数。

1. 对四候选分别运行旧 83 窗口与新增 1,200 窗口。第一轮最早终态 session 的原始产物确定本轮质量输入，包含失败与未执行尾段；恢复 session 和后轮成功结果均不能补齐或替换它。
2. 性能计划采用四轮完整相同输入，候选顺序循环为 `A B C D`、`B C D A`、`C D A B`、`D A B C`；A–D 映射提前随机固定。每轮重新加载，统一预热，预热样本只来自 dev、成本单列；同轮四者使用相同冻结窗口顺序。
3. 冷进程加载时间与文件系统冷缓存不是一回事，不清系统缓存来制造“冷启动”。分别记录加载、预热、prompt evaluation、decode、请求总耗时、端到端耗时和所有重试成本；四轮报中位数及范围。
4. 报窗口/s、计分字幕/s、输入／输出 token/s、生成 token 数、逐窗 p50/p95/p99；不同译文长度下不能仅靠 decode token/s 排名。整片耗时只能按实际规模估算并给误差范围，不能写为整片实测。
5. 对四轮输出按窗口做字节／结构化文本哈希比较。temperature 0 仍需实测一致性；存在差异时报告比例和案例，首轮质量分不替换。若差异广泛影响结论，另建复现稳定性实验，不能把四次得分当四份独立语料。

四候选第一轮均有持久终态或有证据的容量阻碍后，可导出不可变第一轮快照，在 GPU 第二至四轮继续串行运行时
并行执行旧集／新集的裁判。实际网络启动须等待参考和 dev 全部必需任务终结及所属进程排空；
参考、dev、正式评分共用全局最多六个 CLI 的额度及本轮编排器原生字节锁，进程和后代排空后才释放。
性能报告记录并行评分造成的 CPU／RAM／网络负载变化。冻结和离线 readiness 检查不要求占用这六个额度。

容量预检失败的候选不强行执行全部性能轮次；其他候选继续完整测试。环境污染轮次按事前标准（后台显存、服务重启、驱动错误等）标记，保留全部运行，不根据性能数值好坏选择性删轮。

## 8. 语义评估与细微差异判定

严格沿用 `sol-high-auto-v1`：全量机械检查 → 每候选每窗 fresh `gpt-6.1-sol / high` 主评 → 风险并集＋按作品固定 20% 抽样的 fresh 盲复评 → 必要的一次有界裁决 → 程序汇总。复评窗口跨四者取并集，随机规则沿用权威流程的 SHA256 排序，不改为“只看三款与基线不同的字幕”。完全相同译文仍按既有流程独立主评，其评分差异作为裁判噪声诊断，不事后复制有利分数。

裁判只接收匿名 packet，禁止包含候选名、性能或先前窗口对话；主评与盲复评还必须隐藏已有评分及结论。有界裁决按既有流程额外接收匿名、打乱顺序的主评／复评记录，不能把裁决称为盲复评。每个主评／复评任务独立调用；并行调度不等于把多个窗口放进共享对话。worker 显式 `gpt-6.1-sol`、`high`、`fork_turns=none`，输出所有权互不重叠，实际调用身份与原始响应即时保存。模型／effort 不可用即记录阻碍，不静默替换。

有界裁决的合法 `resolved:false` 是已完成的未决结果：须有成功的对应裁决任务、匹配的 canonical
身份和终评 null 字段，保留不确定性并报告数量，不追加调用强行消除分歧。
`judge_failed`、`review_failed`、运行中或缺失任务仍是执行不完整，依赖阶段停止并保留缺分分母。
CLI 调度遇到连续三个不同新任务的同类明确额度／认证／模型访问错误时，停止提交新任务，
排空已提交任务；未提交项记 `not_run` 且返回非零。失败不缩小四候选范围，不因单候选容量失败阻止无关工程工作。

报告保留以下层次：

- 主指标：逐窗语义 0–4，作品内均值后按作品等权，剧集与电影分别报告；可附预声明的两类各 50% 总览。自然度 0–2 单列，不加成总分。
- 严重错误：最终支持的 major／critical 错误数及涉及窗口比例，四者共同覆盖范围、未决范围、初评与终评变化均公开；同一根因不重复计罚。
- 交付：首次／最终成功率、漏 ID、截断、语言异常疑点、重试及全部终态。假名／专名保留不自动判未翻译；GBNF 通过不证明内容正确。
- 细分：各作品、各集、位置、长度和源侧风险标签；同一术语的跨窗译法一致性作为诊断，允许正当别名。非概率挑选案例不用于总体错误率。
- 缺分：翻译交付零分与 setup／裁判／映射不可评分开；所有预期窗口留在分母，语义缺分以 0／4 填补计算上下界。未执行尾段另记 `not_run` 的调度状态，不能伪造现有翻译账本中的 `translation_failed`；接跑前补齐，仍阻塞时以缺分界呈现。上下界不是置信区间。

三个新候选各自对基线做预先指定的配对比较，旧回归与新主集分别分析。保留完整配对窗口的胜／平／负、配对覆盖和语义差；以作品为簇在类别内配对 bootstrap 10,000 次、seed `20261006`，保持作品等权。主表展示普通 95% 区间；若据区间提出任一新候选“优于基线”的正式结论，同时给三个对照各 98.33% 区间作为 Bonferroni 家族错误控制近似，电影／剧集各自明确结论范围。若主张跨两类别任何一处获胜，还需把六项比较共同校正，不能事后选类别。

作品少使 bootstrap 的覆盖保证有限；补充逐个移除作品、合并同系列作品的敏感性分析，不能把字幕行当独立样本增加显著性。所有置信区间只描述可评分配对子集，完整分母缺分界仍为优先约束。

**选择原则**：只有新主集显示可重复、非单作品驱动的收益，严重错误／交付没有相反证据，且显存和耗时可接受，才建议更换。统计可区分不等于收益值得成本；报告绝对差值及代价供用户选择。差异落在评审不稳定范围、区间跨零或缺分可翻转排序时，结论写“未能稳定区分”。不因没有显著差异声称等效，也不为了分出胜负追加抽样直到显著。

## 9. 工作量、执行阶段与完成条件

按新增 1,200＋旧 83＝每候选 1,283 个质量窗口预算，实际数以冻结 manifest 为准：

| 项目 | 预算口径 |
| --- | --- |
| 新参考构建 | 至少 2,400 次窗口级审核判断，另加排除／候补和必要裁决；可做调度分片，不省第二轮独立复核 |
| 四候选质量主评 | 5,132 个逻辑任务，dev 联调另计 |
| 盲复评 | `4 × R`；R 为风险并集＋固定抽样窗口数，约 20% 起，最坏全部 1,283 窗口 |
| 裁决 | 按实际分歧计，最多每候选每窗一次；主评＋复评＋裁决最坏 15,396 个逻辑任务 |
| 裁判失败重试 | 每逻辑任务最多一次 schema／传输重试；质量评估最坏 30,792 次调用尝试，不含参考建设和 dev |
| 本地性能推理 | 四候选×1,283×四轮＝20,528 次窗口运行，另计 dev、预热、重试和长跑 |

瓶颈很可能是参考审核与裁判，而非本地翻译；不能沿用旧 83 窗口生成约一分钟来承诺总任务耗时。先用完整 smoke/dev 测各阶段每任务耗时、并行有效吞吐、失败率、可见 token／额度成本，再给带 20% 调度余量的预算。主评、复评和裁决按阶段依赖计算，不能把全部任务视为可同时启动。额度不足则保存明确未完成清单并接跑，不悄悄缩成小样本。

| 阶段 | 完成条件 |
| --- | --- |
| A：资产与 demo 接入 | 四款身份、metadata、引擎与实际输入核对；离线检查、完整 smoke/dev；容量不可行者留明确证据 |
