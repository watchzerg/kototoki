# TranslateGemma 字幕翻译流程草案

状态：draft；原生接口边界已核查，完整增强流程尚未实现；固定窗口原生翻译与辅助映射子集已有 demo 和实测。  
最后更新：2026-10-07。  
范围：本地日语→简体中文字幕；以 Google TranslateGemma 12B 的原生文本翻译契约为起点，兼顾已获取的 12B Q8_0 与 27B Q3_K_L GGUF。本文只设计后续翻译实验，不改变当前保留原语言的 STT 里程碑、W0／X0 或已采纳模型。

当前字幕翻译基线为 Hy-MT2 30B-A3B APEX-I-Compact，见[ADR-0005](../adr/0005-apex-i-compact-translation-baseline.md)；TranslateGemma 保留独立对照身份。已完成的固定窗口比较从[评估入口](../testing/translation-model-evaluation.md)检索，下文完整增强流程仍属草案。

共同的数据、时间、失败记账与评测边界由[共同流程](subtitle-translation-common.md)定义。可遵循只读上下文、术语与结构化任务指令的模型见[通用指令模型流程](subtitle-translation-generic.md)。既有证据见[TranslateGemma 专项研究](../research/2026-10-05-translategemma-12b-local-translation.md)、[三模型接口比较](../research/2026-10-05-local-translation-model-comparison.md)、[字幕流程研究](../research/2026-10-05-subtitle-translation.md)、[量化研究](../research/2026-10-06-translation-5080-quantization.md)与[资产入口](../guides/local-translation-model-assets.md)。

## 1. 方案判断与不可假定的能力

TranslateGemma 可以把多条短 cue 合成完整句、话轮或有界段落再译；ID、源跨度与时间可以由程序保存。因此原生最小方案不需要逐句调用，也不需要模型生成 ID。若一个请求包含多个分别有时间锚点的 TranslationUnit，纯段落译文就需要额外的双语映射环节；没有已验证的方法可以只凭分隔符数量自动恢复对应。

官方模型卡规定：仅 `user`／`assistant` 角色；每条 `user.content` 恰好一个条目，文本条目含 `type`、`source_lang_code`、`target_lang_code`、`text`；`text` 仅为待译材料，输出为目标语言译文。12B 与 27B 模型卡均写总输入上下文 2K tokens。可构造一条包含多段正文的输入，但这不建立多 ID 输出、JSON schema 或 SRT 输出的契约。[12B 官方卡](https://huggingface.co/google/translategemma-12b-it)、[27B 官方卡](https://huggingface.co/google/translategemma-27b-it)

Google 团队明确说明，没有单独的 system prompt 或普通指令参数；加入 `text` 的信息会被作为源文翻译，术语与风格不能通过一般 LLM 的提示方式强制执行。[Google 团队答复](https://huggingface.co/google/translategemma-12b-it/discussions/2)

| 需求 | 原生路径如何处理 | 可选实验与边界 |
| --- | --- | --- |
| 多个源 cue 一起理解 | 合成一个合法语义单元，将整个单元作为正文 | 保留原文跨度；合并不能越过保护边界 |
| 一个请求多个单元 | 将多个自然段作为整块待译正文 | 输出仅为字符串；额外映射及其失败属于流程成本 |
| 前后文只读、不翻译 | 无原生字段 | 前后文一起翻译后由辅助映射抽取核心；不能按行数直接裁掉 |
| 标题、剧情、人物关系 | 存在程序 sidecar，辅助分析／映射时按需使用 | 放进原生 `text` 就成为待译内容，不能声称只参考 |
| glossary | 程序校验词名与称呼一致性 | 需修复时交给另行配置并验证的修订模型或人工；占位符方案单列实验 |
| 多 ID JSON | 程序包装单元／块结果 | 不让原生模型承担协议；强制 grammar 不能证明 ID 对应 |
| 历史摘要／compact | 原生基准每次新请求，不携带历史 | 仅在辅助模型维护源文事实；直接送入 TranslateGemma 属非标准实验 |

Google Cookbook 用 4B 示范两段连续正文翻译，说明家族可按文档正文使用；它没有验证 12B 的日中字幕边界、术语或时间映射。[Google Cookbook](https://raw.githubusercontent.com/google-gemini/gemma-cookbook/main/Research/%5BTranslateGemma%5DExample.ipynb)

## 2. 模型身份、模板与预算

### 2.1 保持原生契约

本轮实际适配（2026-10-06）：已下载的 12B／27B GGUF 原生语言表均支持 `ja` 与 `zh-Hans`，不含 `zh-CN`。因此[五版本实验](../plans/translation-model-comparison.md)显式采用与冻结模型输入一致的 `ja→zh-Hans`，并记录模板与渲染哈希；两组输入与真实 Jinja 的逐字节对照通过，证据见[执行记录](../context/2026-10-06-translation-comparison-execution.md)。下方 `zh-CN` 是原设计候选示例，不是当前已验证的运行参数。此变化不扩大源上下文或改动参考库。

候选语言码设为 `ja`→`zh-CN`，但它们是否被所选 checkpoint／GGUF 中的模板确切接受，必须先作模板渲染检查。官方允许简码与地区码，并在不支持时报错；这不等于允许任意地区码。不要擅自把 `zh-CN` 替成 `zh`、`zh-Hans` 或默认英文后继续算成功。[官方语言码规则](https://huggingface.co/google/translategemma-12b-it#usage)

本轮匿名 web 访问官方 `chat_template.jinja` 的 raw／blob／resolve 路径均未成功，未逐字符审计该模板，也未读取本地 GGUF 的模板。部署前需从固定模型文件确认：语言码映射、Gemma 控制 token、待译材料位置、model turn 和停止 token；将渲染结果与模板哈希存入运行身份。使用 Transformers 时由实际 processor／tokenizer 渲染，不手工拼一个“差不多”的聊天提示。GGUF 适配器是否能接收同样消息对象是引擎问题；若通过模板 kwargs 传语言码，记录准确字段和最终 prompt，不把下面消息对象直接当成每个 OpenAI-compatible server 都能处理的请求。

llama.cpp 提供模板选择与 `/apply-template` 预渲染能力，可作为后续适配核查入口；应冻结实际稳定版本并核实该版本行为，不沿用某个历史 PR 的默认英文参数。[llama.cpp server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

### 2.2 原生请求示例

以下为自行编写的合成例子和应用层设计，尚未发给模型。两个 cue 属同一说话人的紧邻话轮，中间无保护性停顿；若实际有悬念停顿或换人，须拆单元。

```json
{
  "source_cues": [
    {"id": "s101", "start_ms": 10000, "end_ms": 11600, "text": "鍵は机の上に置いた。"},
    {"id": "s102", "start_ms": 11600, "end_ms": 13900, "text": "戻るまで、誰にも渡さないで。"}
  ],
  "unit": {"id": "u041", "source_cue_ids": ["s101", "s102"]}
}
```

程序保存上面的 ID 与时间，仅把合成正文送给原生翻译接口：

```json
[
  {
    "role": "user",
    "content": [
      {
        "type": "text",
        "source_lang_code": "ja",
        "target_lang_code": "zh-CN",
        "text": "鍵は机の上に置いた。戻るまで、誰にも渡さないで。"
      }
    ]
  }
]
```

模拟译文是 `钥匙放在桌上了。我回来之前，别交给任何人。`，仅为协议说明，不是候选模型结果。程序把新生成的字符串包装为下列内部记录；`u041` 的对应由请求关联取得，不依赖模型回显编号。

```json
{
  "unit_id": "u041",
  "source_cue_ids": ["s101", "s102"],
  "translation": "钥匙放在桌上了。我回来之前，别交给任何人。",
  "mapping_kind": "request_unit",
  "status": "needs_review"
}
```

返回字符串完整不代表其意义准确，也不意味着已把中文恢复为两个时间正确的 cue。不得默认用输出第一句配 `s101`、第二句配 `s102`；此例可以这样人工关联，其他输入可能合句、倒装或改变标点。

本地生成接口只解码新生成的 token 后缀，不能把输入模板／源文一起 decode 后误存为译文。服务接口则从其已验证的正文响应字段取值，移除运行器控制 token 后保留完整文字；不自动剥掉看似“多余”的句子。第一份确定性控制可采用 `do_sample=False` 或后端等价配置，生成上限按下节预算设置；这是待测配方，不能把某个引擎的默认值当作所有部署一致的模型参数。

### 2.3 输入与输出分开计数

原生实验令 `I = tokens(rendered_prompt)`，包含控制 token、固定译者说明与所有正文；以 `I ≤ 2048` 作为对模型卡 2K 的实验上限解释，实际输入仍留余量，精确硬限制取所选运行时与模型适用限制的较小值。输出另预留 `O`，同时满足实际序列窗口 `I + O + safety_margin ≤ C_runtime`。2K 是官方输入范围，不能误记成输入加输出的总长度，也不能从 Gemma 3 的位置容量推定更长翻译已获验证。

首轮可试 `I_target = 1024–1536`、`O = 768`、运行窗口 4096 的配置；这些是待测起点，不是官方最优值或能容纳任意字幕的保证。使用真实 tokenizer 计算每次预算；中文输出比例由 dev 样本估计并留余量。到达输出上限／停止状态异常即标截断，不能通过截断文本满足阅读速度。超预算时先减少待译单元和可选邻文，完整语义单元本身超限才在可追溯子跨度边界拆分；禁止静默 tokenizer truncation。

已获取 12B Q8_0 文件约 11.65 GiB、27B Q3_K_L 约 13.54 GiB；文件大小不是峰值显存。固定 revision、哈希与路径沿用[资产入口](../guides/local-translation-model-assets.md)。12B／27B 的固定窗口运行、模板、资源及质量证据见[五候选报告](../research/2026-10-06-translation-model-comparison-results.md)，不能据此宣布下文增强流程已验证。模型越大但量化更低不能据参数量预先判优。STT 与辅助模型按阶段卸载，记录加载、切换、KV cache 与峰值显存；新流程或并发须独立验证。

## 3. 语义单元、Chunk 与标记

SourceCue 的 ID、文本、时间保持不可变。TranslationUnit 用稳定 ID 关联源 cue／字符跨度，可以合并多个被显示切开的 cue，优先形成完整句、短话轮或连贯短段落。禁止跨说话人、明显长静音、场景切换、重叠轨道及揭示顺序等保护边界强行合并；无法确认说话人时保留不确定性，不用翻译模型猜出可靠 speaker label。具体保护规则按[共同流程](subtitle-translation-common.md)冻结。

Chunk 可装多个单元。必须明确其实际用途：

- **独立序列 batch**：每个 TranslationUnit 各有原生请求和生成序列，程序保序配 ID；同 batch 只共享 GPU 调度，不共享上下文。可按相近 token 数分组以减少 padding，吞吐仍需实测。[Transformers batching](https://huggingface.co/docs/transformers/en/main_classes/pipelines#pipeline-batching)
- **共享正文 Chunk**：几个单元的原文进入一个 `text`，由一个序列翻译整块；相邻内容可提供语境，但只有 Chunk 级外部关联。需要下节的额外映射，不能把输出按 batch 位置配回各单元。

用户希望“多条加标签，一段翻译”的方式可以作为探索组，例如：

```text
<u041>鍵は机の上に置いた。戻るまで、誰にも渡さないで。</u041>
<u042>わかった。窓も閉めておく。</u042>
```

这在语法上仍是一个 `text`，但标签本身成为待译材料；没有原生“保留标签、分别返回”的指令支持。标签被保留、数量正确甚至顺序正确，都不证明中间中文属于正确原文。默认推荐无标签自然正文＋外部跨度表；带标签组用于测量是否帮助映射，不是可靠协议。不要加入“只翻译标签里面、返回 JSON”后继续称作原生控制组。强制 JSON grammar 只约束引擎输出语法；其与模型任务的一致性、遗漏及映射都要另测。[llama.cpp grammar 文档](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)

## 4. 最小原生流程

`SourceCue → TranslationUnit → 原生纯文本翻译 → 程序关联单元 → 显示重组／审查`。

1. 在确定的局部保护边界内形成单元，保存 cue IDs、源字符跨度与时间锚点；每个单元可覆盖数条 cue，无需逐 cue 调用。
2. 每个单元开启新原生请求。相同请求 identity 可复用缓存；可小 batch 并发，按应用任务 ID 配回，不能只依赖完成顺序。
3. 检查服务状态、停止原因、空结果、源文复制与错语言疑点，程序建立单元外层 JSON。该关联确定记录的来源，语义完整仍待审查。
4. 只有整个单元的连续时间跨度已经适合显示，且不会越过停顿／换人／提前揭示边界，才允许显示为该跨度内的一条字幕。保留 `coarse_unit` 时间精度标记，不能宣称达到原 cue 或词级同步。
5. 对过长、跨多个信息时刻、阅读负担过高或需保留原 cue 时间的单元，进入辅助映射／人工重组；不按中文字数比例分毫秒，不把中文送入日语单语 forced aligner。

最小流程的实际限制是：语义单元越大，输入语境越完整，但仅有单元级时间的中文越难精细同步。无法获得可靠细分时应保留待处理状态或缩小单元，不能复制整段译文到所有源 cue、均分字符或把原文回填后记作成功。

## 5. 段落联合翻译＋辅助映射

这是满足“多单元共享正文、允许自由中文表达、仍能重建时间轴”的候选流程，需要通用模型／双语人工参与；并非 TranslateGemma 自身提供的接口能力。

### 5.1 输入与只读邻文

程序为 Chunk 保存两种范围：待交付的核心单元，以及前后相邻原文。原生 `text` 拼接 `prefix_source + core_source + suffix_source`，其中全部材料均翻译。邻文优先完整短话轮，同场景优先，按 token 预算限量；不设固定“前 3 行、后 2 行”适用于所有语速。先用短邻文，与完全不加邻文作配对对照。

译后映射器看到带 ID 的核心／邻文源跨度表和整块中文，关联哪些目标片段来自核心、哪些来自邻文。它可以利用只读元数据、相关术语与源文事实，但不能补写剧情。核心外译文不直接进最终输出；保存其完整结果以审计抽取是否误删、误留或将后文答案提前挪到核心。

加邻文会重复翻译重叠部分，增加输入和输出；它解决的是原生缺少只读 context 的限制，并非免费 prefix/suffix。若译文跨核心与邻文合句，不能用中文行数、首尾字符串相似或预期译文长度裁切。映射无可靠边界就缩邻文／拆 Chunk 重译，或交人工；禁止猜测核心文本。

### 5.2 映射器只提出关联，程序验证

映射器首先执行**不改写中文的关联**：以 Unicode code point 的半开区间 `[start, end)` 指向完整原生输出，提出每个 TranslationUnit 的中文跨度和源跨度关联；一个中文句可以关联多个源 cue。区间应覆盖应交付的中文、不重复消费、没有悬空文本，源核心跨度全部有记账。允许单元内语序改变，但不能跨保护边界重新分配意思。

例如合成原生输出 `别说出去。好。`，程序登记前句源单元 `u_ref` 为邻文、后句 `u_core` 为核心。映射器可以提出如下结果；区间和归属均需检验，不能因示例正确就直接推广到实际模型输出：

```json
{
  "assignments": [
    {"unit_id": "u_ref", "target_spans": [[0, 5]]},
    {"unit_id": "u_core", "target_spans": [[5, 7]]}
  ]
}
```

核心／邻文身份来自请求清单，不让映射器自行决定哪些内容该丢弃。程序检查全段 `[0,7)` 恰好覆盖一次，再按清单只交付 `u_core` 的 `好。`；邻文译文仍留在审计记录。一般情况下空白／标点也需有明确归属，所有区间必须用 `output[start:end]` 精确还原；不能通过舍弃无法定位的文字来达到覆盖率。

纯结构可确定验证 ID 集、区间合法、源／目标覆盖与顺序约束；它们不能确定验证含义正确。人工／独立双语审校抽查否定、专名、数字、代词、谁对谁说，以及核心与邻文的语义归属。辅助模型自报 confidence 仅作排序信号，不能作为自动放行证据。日中双语重排严重时，连续区间可能无法在不改写的条件下对应原 cue；应记录 `mapping_failed`，不能为追求覆盖率伪造区间。

需要改写成可分别显示的字幕时，另启**目标编辑**步骤，输出草案与相对原生译文的差异，明确不是纯映射。重新审查遗漏／增译及目标跨度；保留初稿和修改理由。模型合成的关联或改写不自动赋予精确时间。

### 5.3 时间重建与成本

程序从不可变源时间锚点导出目标 cue，绝不采用模型生成的新时间码。只有原 cue 时间时，允许的关联必须落在其可信连续范围；细分精度为 cue／单元级。已有可信日语词级时间时可以通过双语关联传播到中文，但关联错误仍会导致错时；不能称为中文与日语音频的直接声学对齐。按共同显示规则检查时序、停顿、说话人、阅读负担和信息揭示；异常保留待审查。

这条路线的全成本为 `预分析 + TranslateGemma输入/输出 + 映射 + 可选编辑 + 校验 + 重试 + 模型加载切换`。额外步骤可能超过省下的逐单元调用成本；在 16 GB 单卡上共驻显存不能默认成立。先分阶段缓存译文再切换辅助模型，记录冷启动与已加载状态的时间。报告每分钟源内容的总耗时、每块追加 token、失败重试比例及人工修订量，不只报告 TranslateGemma tokens/s。

## 6. 预分析、glossary 与状态

可选便宜的本地通用模型从源日文做全片或局部预分析，产出标题来源、人物／别名候选、术语候选、场景主题与未决指代；每项带源 ID、已知时刻、来源与不确定状态。它不替代原文，不改时间，不从中文参考提取“正确答案”。模型可处理全片的前提是其真实 tokenizer／运行预算足够；否则按场景分段后汇总，而非静默截断。

只读开头 8000 字符是廉价候选，必须标为“开头样本”，不是全片摘要；后半角色和情节可能缺失。对照至少包括无预分析、开头 8000 字符和源文全片／分场景汇总。英文数字“8000”是字符采样预算，不是 TranslateGemma token 上限，也不是证明有充分背景的门槛。既有 VideoLingo 调研记录其默认开头采样与主题术语步骤，可作为实验启发，不能直接迁移为本模型受支持提示。[VideoLingo 源码调研](../research/2026-10-05-translation-videolingo.md)

这些信息默认用于单元边界建议、译后术语校验和辅助映射／编辑，不注入原生 TranslateGemma 正文。人物称呼不能因全片后来揭示身份就提前替换当前含糊表达；跨片知识仅作为有来源的候选，具体台词优先。glossary 按当前 Chunk 检索命中项；译后只在有明确词名边界和语法依据时机械替换，否则进入编辑审查。占位符替换可能被吞掉、重排或影响敬称，需单列挑战集，不能承诺锁定术语。

| 状态方案 | 设计选择 | 风险／代价 |
| --- | --- | --- |
| 每批新上下文 | 原生默认；辅助步骤也只读固定源文与该 Chunk 材料 | 可并行、易重现，局部消歧可能不足 |
| 固定源文场景摘要 | 辅助步骤读有 ID 的源文摘要，各批相互独立 | 摘要遗漏、预分析成本与后文提前泄露需审查 |
| 前批结果 compact | 仅辅助模型实验；保存已接受译名、原文事实、未决项 | 前批译错会强化；状态顺序依赖阻碍并发 |

滚动状态需绑定版本、上游 Chunk ID 与状态哈希；先复核前批结果再更新，不把失败初稿压入摘要。场景变化时重置短期状态；能够从原文重建的事实优先重新核对。重跑某批若改变 accepted 状态，下游缓存失效或另建分支。不能同时并发全部 Chunk 又声称它们都使用最新前批 compact。直接向 TranslateGemma 历史轮次塞摘要、术语或元数据属于非标准 prompt 实验，即使模板接受 assistant 历史也不证明参考信息不会被译出。

### 6.1 可选反思阶段

原生翻译之后可增加“结构检查→可选审校→必要修订→再校验”，采用[共同设计第 9.1 节](subtitle-translation-common.md#91-可选反思审校修订与再校验)的 `off`／`on_demand`／`all` 模式。**审校与修订使用本模型还是其他模型暂不固定，均通过独立 profile 配置。** 这项设计选择不改变 TranslateGemma 的原生接口事实：复用本模型执行审校／后编辑须作为非标准提示实验验证，不能把源文、初译和纠错指令直接塞入原生 `text` 后声称这是官方审校接口。配置其他模型也须验证其能力，不因不同模型就默认更可靠。

最小单元路径在程序绑定 unit ID 后审校；联合段落路径可以先审查整段忠实度，但在映射通过前不得输出伪造的逐 unit 修订。逐 ID 修订需要已经验证的源译关联；关联失败仍走第 5 节的恢复流程，反思不能替代映射检查。

输入为源文、完整原生初译、核心／邻文清单、已有映射及精度、译文版本、允许修改范围、必要背景和适用术语。审校逐项记录 `keep`／`revise`／`unresolved`、问题及源证据，重点检查遗漏／增写、否定／人物关系、术语和核心／邻文污染。参考只能来自该评测轨允许的信息，不能从参考答案或裁判反馈补充。

修订明确生成新的目标文本版本，与第 5 节“不改字”的纯映射步骤区分。初译、反馈和修订均保留；任一文字变化都会使旧目标字符 offset 失效，必须重新做核心抽取、源译映射、显示切分和语义检查，不能复用初稿的区间。源 ID、跨度和时间保持不变。

建议初试一轮审校及至多一轮必要修订，角色可以共用模型、分用模型或合并调用，但总成本及所有重试计入共同预算。模型／模板不支持、失败或收益不明确时记录限制、保留初稿与未决状态，不静默切换模型，不将修订失败记作已通过审校。

关闭反思、同模型实验及其他模型方案分开比较；报告初译和最终流程的纠错／新增错误、映射失效与恢复、未决项、总耗时及加载切换。反思结果不冒充原生纯翻译质量，也不混入原版 `V2-replay`。

## 7. 错误恢复与优化

| 失败／疑点 | 有界恢复 | 禁止的放行方式 |
| --- | --- | --- |
| 模板或语言码拒绝 | 修复 adapter，重新渲染，重做短 smoke；配置修正另记身份 | 默认退英文／普通 Gemma chat |
| 输入超预算 | 在语义边界减核心／邻文，重新计数 | 静默截断源文或 glossary |
| 输出截断、空白、解释或错语种 | 检查停止原因与模板；每个原请求最多一次重试，再缩范围 | 截断／补原文后记成功 |
| 标记缺失／多出或行数变化 | 不据标记判 mapping；交辅助映射，失败则拆 Chunk | 第 n 行自动配第 n 个 ID |
| 映射漏源／重目标／核心污染 | 机械验证拒绝；缩邻文或减少单元后重译，仍失败转人工 | 填猜测区间、丢弃不能定位文本 |
| glossary／人物关系疑点 | 带源证据审校或目标编辑，保留原稿 | 无边界全局字符串替换 |
| OOM | 先减并发／窗口，重测驻留；改变精度另记模型身份 | 静默 CPU offload 或换量化后混报 |

每个 Chunk 的自动恢复最多采用两级语义拆分，最终有明确失败状态；次数是拟议默认，可在 dev 阶段冻结调整。拆分辅助段落时保留必要邻文，计入重复生成成本；不可在原生上下文未拆开之前擅自接受其中看似成功的局部文本。关键否定、数字、指代或跨单元依赖出错时按最小依赖组重审。

可先优化：加载复用、近长度 batch、按预算组块、只审异常、只检索相关术语、缓存固定预分析、缓存未变化的请求。缓存键至少包含源／目标语言、源跨度及文本、核心／邻文、模型／GGUF哈希、模板／adapter版本、解码预算／参数和辅助状态版本。禁止仅以原文字符串缓存，特别是同一句“わかった”在不同人物关系或历史下的结果。

原生固定模板前缀较短；cache 是否有效由后端实现与实际命中决定。辅助模型的稳定元数据可放静态前缀，但不应为 cache 命中扩大敏感素材范围。先记录完整可靠单请求控制组，再增加 batch；对 27B 低位量化应独立测否定、专名、重复和映射，不以“能加载”或“比 12B 大”作为晋级理由。

## 8. 评测身份与验收实验

现有[评估入口](../testing/translation-model-evaluation.md)及 v2 规约是固定参考，具体三种身份由[共同流程](subtitle-translation-common.md)维护：`V2-replay` 精确复现历史协议；原有 system／prompt／带 ID 输出与本模型原生契约不兼容时明确记录不适用，不强套；`V2-native-adapted` 保持同一隔离源输入，声明原生模板与外部 ID／映射适配；`P-flow` 才评估扩展源上下文、全片预分析和滚动状态。不得将扩展流程成绩当成原 v2 成绩。

v2 逐窗口新状态的运行不能读其他窗口的记忆、全片预分析或中文参考。纯段落＋辅助映射的成绩反映两个模型与完整流程，不是 TranslateGemma 单独的原生翻译质量；辅助模型身份、输入范围、成本、失败必须同时报告。

| 阶段 | 对照 | 验收问题 |
| --- | --- | --- |
| 模板预检 | 12B／27B 固定文件，显式 `ja`→`zh-CN` | 接受的准确语言码、最终译者 prompt、特殊 token、停止条件是否一致？ |
| 合成挑战 | 合句、重复短句、跨 cue 否定、数字、人名／敬称、长停顿、换人、重叠轨 | 源覆盖、信息出现时机、目标语种和保护边界是否可靠？ |
| 原生质量 | 逐 cue；合并完整单元；单元独立 batch | 合并是否改善错意／自然度，batch 是否只影响吞吐和资源？ |
| 联合段落 | 无标记；标记；无邻文；带邻文 | 合漏句、串单元、标记损坏、核心抽取和辅助映射失败多少？ |
| 辅助与状态 | 无辅助；映射；必要编辑；源文预分析；滚动 compact | 每项净质量改善是否抵得过耗时、显存切换与人工量？ |
| 模型资源 | 12B Q8_0；27B Q3_K_L | 相同输入／流程下真实日中质量、截断、峰值显存与全链路成本如何？ |

首轮先对 v2 smoke 做接口检查，再锁定 dev 规则与固定 test；扩展 P-flow 用独立源素材／manifest，按片与连续场景分别报告。参考译文未经音画人工审定的限制继续有效；背景事实不能从 reference 或 judge 反馈进入候选 prompt。

放行到下一实验阶段前，确定性约束必须全部满足：来源身份可追溯、核心源跨度完整记账、ID／区间合法、目标文本无非预期重复消费、时间不越过保护边界、截断／失败可见。语义验收另做盲审，报告严重错意、遗漏／增译、指代、否定、专名、术语、核心／邻文串译与信息过早显示；结构全过不是语义全过。再分别报告 CPS／CPL／行数与播放审查、单请求和整流程时间、失败分母、重试和人工修订量。

本草案没有已测合格率、默认合并时长、最佳 Chunk 大小或推理参数；这些须在 dev 固定，不能用 test 结果反复调参。全链路质量与 Native bare quality 分开记，保留原稿、辅助输出与失败记录。[验证边界](../testing/validation.md)规定文档变更只需链接与一致性核查；本次不以未运行的模型作为验证证据。
