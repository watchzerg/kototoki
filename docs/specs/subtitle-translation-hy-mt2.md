# Hy-MT2 字幕翻译流程提案

状态：draft；完整增强流程尚未实现，固定窗口 JSON／GBNF 子集已有 demo 和实测，其余批量与增强协议仍待验证。  
最后更新：2026-10-07。
范围：本地日语→简体中文字幕；当前基线为 **Hy-MT2 30B-A3B APEX-I-Compact**（`hy-mt2-30b-a3b-apex-i-compact`），见[ADR-0005](../adr/0005-apex-i-compact-translation-baseline.md)与[demo](../../experiments/translation_demo/README.md)。7B Q8_0、30B-A3B Q3_K_M 及其他量化保留独立对照身份。本文不改变当前 STT 基线，不把翻译接入已实现的产品能力。

共同的数据身份、受保护边界、时间与显示规则以[字幕翻译共同契约](subtitle-translation-common.md)为准。本文讨论 Hy-MT2 的输入适配、请求组织、返回校验与恢复。证据入口为[模型专项研究](../research/2026-10-05-hy-mt2-7b-local-translation.md)、[流程复核](../research/2026-10-06-hy-mt2-subtitle-flow-review.md)、[三模型比较](../research/2026-10-05-local-translation-model-comparison.md)、[量化研究](../research/2026-10-06-translation-5080-quantization.md)和[本地资产入口](../guides/local-translation-model-assets.md)。

固定 APEX 模型后的系统探索见[翻译模式优化计划](../plans/hy-mt2-translation-mode-optimization.md)。本文的优先路径仍是候选，不限制新计划比较其他格式或完整 SRT→SRT 架构；评估采用已采纳的[自动评估流程](../agents/subtitle-translation-evaluation.md)，不安排人工日语复核。

**本文是可迭代的设计草案。** 源记录不可变、内容归属可追溯、失败不得伪装成功、评测输入隔离是贯穿各候选路径的约束；请求格式、分段策略、上下文范围、模块组合、采样、批量、窗口和恢复次数均可在实现中边试边调整。下文的推荐顺序与数值只是实验起点，不是固定产品流程，也不要求一次实现全部增强。探索阶段记录每次变化及观察；需要比较结果时，冻结该轮输入和实际配方，下一轮仍可修改。性能或质量改善经验证后再更新推荐，不能把不同配方混成同一结果。

## 1. 推荐起点与证据边界

推荐按完整句／有界话轮合并源 cue，形成带稳定 ID 的 `TranslationUnit`，按语义与预算组织 `Chunk`。优先从新的单条 `user` 请求开始，按需携带相关术语、短背景和只读邻接原文。保留两条可正常使用的候选路径：

| 路径 | 请求与结果 | 待验证的取舍 |
| --- | --- | --- |
| 单单元纯文本 | 每个合并语义单元独立请求，仅生成译文，由程序绑定 ID 并包装结果 | 接口简单，可带只读邻文；重复输入、独立请求成本及跨句一致性需实测 |
| 多单元结构保持 | 多个单元共用请求，探索只翻译 JSON 正文并保留 ID 与结构 | 可能改善吞吐或连贯性，也可能增加串段、结构失败及恢复成本 |

单单元路径既可作为初始控制，也可长期使用，不必先经历批量失败。多单元路径是否成为主要模式，按质量和含恢复的总耗时决定；两者也可按明确记录的规则组合。**这是待测流程，不是已证明稳定的批量接口。**

| 事项 | 已核验依据 | 本提案的使用方式 |
| --- | --- | --- |
| 语言与指令 | 官方语言表包含日语和中文；提供术语、背景、风格、分隔符和结构保持示例 | 目标明确写“简体中文”；逐项测条件叠加，不推定字幕质量 |
| 输入字段 | 官方推理示例使用单条 `user` 的文本 `content` | `title`、背景、术语及只读上下文均是应用生成的 prompt 段，不是模型的独立 API 参数 |
| 原生包装 | 7B 使用 `<|startoftext|>`／`<|extra_0|>`；当前 30B 使用 Hunyuan 特殊 token、`reasoning_effort:no_think` 与空 think 前缀，见[实际适配器](../../experiments/translation_demo/adapters.py) | 核对所选 GGUF 模板；消息接口与手工渲染二选一，避免重复包装，不套通用 ChatML |
| 多单元返回 | 官方有结构数据选择性翻译范式 | 试最小 ID＋正文 JSON；程序检查 ID、覆盖和语义，不能只检查数组长度 |
| 窗口 | 官方仓库部署说明写 `max_context: 8192` | 以实际 runtime 窗口与此初始边界的较小值预算；配置中的更大容量不视作已验证长文窗口 |

以上事实分别见[官方任务示例](https://huggingface.co/tencent/Hy-MT2-7B-GGUF#hy-mt2-translation-task-instruction-examples-chinese-english-comparison)、[官方 chat template](https://huggingface.co/tencent/Hy-MT2-7B/blob/main/chat_template.jinja)、[部署说明](https://github.com/Tencent-Hunyuan/Hy-MT2#inference-and-deployment)，访问日期均为 2026-10-06。

官方默认中文任务句如下，可用于单单元无增强控制：

```text
将以下文本翻译为 {target_lang}，注意只需要输出翻译后的结果，不要额外解释：
{source_text}
```

这里用完整中文语言名替换 `{target_lang}`。背景和术语模板的准确原文在上方官方任务示例；下文是组合后的字幕提案，不能称为官方字幕模板。模板源码能表示 `system` 和多轮，但不证明长历史的翻译效果；本路线首先不携带聊天历史。

官方 IFMTBench 的 JSON 检查比较类型、键集合与数组长度，不验证字符串 ID 值是否保持不变；布局检查比较分隔后块数。应用必须补充内容归属检查。[官方验证源码](https://github.com/Tencent-Hunyuan/Hy-MT2/blob/main/IFMTBench/eval/rule_validators.py)，访问日期 2026-10-06。论文展示了字幕指令案例；家族案例不能推出本机 7B Q8 的通过率，量化后的翻译分数与指令遵循也应分开评价。[技术报告 v1，§3.5–3.6](https://arxiv.org/html/2605.22064v1)，访问日期 2026-10-06。

### 实验协议隔离

下文描述的是拟议流程能力，实际运行必须选择共同契约中的一种协议并冻结输入：

| 协议 | Hy-MT2 的边界 |
| --- | --- |
| `V2-replay` | 精确复现 v2 继承的历史提示与输入；不因为本模型支持背景就改变模板，不增加标题、完整影片或历史摘要 |
| `V2-native-adapted` | 同一 JSONL 窗口和原有可用信息，以 Hy-MT2 原生模板创建新请求；这是新协议，明确记录 prompt、单元合并、返回格式和预算变化，不归入历史分数 |
| `P-flow` | 完整影片预处理、额外有来源背景、术语准备及滚动记忆另立 manifest 和配方；不能同冻结 v2 结果混记 |

可选材料不存在于冻结输入时，相关段落必须为空或省略。完整影片预分析即使不读取参考译文，也会扩大源信息范围，仍属于 `P-flow`。`P-flow` 优先使用新请求＋显式原文上下文，源摘要按需试验，不是必经步骤；持续聊天是进一步独立对照。

`V2-native-adapted` 的最终结果仍须保持原窗口 `translate_ids`。如内部合并为新的 unit，必须另行验证译文能否忠实拆回原计分 ID；不能直接用 `u041` 等内部 ID 替代计分 ID，或将相同长译文复制到多个条目。无法拆回时记录映射失败；使用辅助模型拆回则属于 assisted 子轨，单列身份、耗时和错误。

## 2. 输入准备与语义单元

1. 读取原文 SRT 或带字符时间锚点的 STT sidecar；保存输入哈希。`SourceCue` 的 ID、原文和起止时间不可变；正文清洗另存视图与映射，不能覆盖源记录。
2. 将被显示换行打断的完整句、连续话轮合并为 `TranslationUnit`。每个单元具有稳定 ID 和不可变源跨度；一个单元可以覆盖多个 cue，内部可以调整中文语序。合并不跨已标记的说话人切换、场景／时间断点或信息揭示边界；不因 token 余量而扩大跨界范围。
3. 在语义边界组织 `Chunk`，其中可包含一个或多个待译单元。相邻不同说话人的单元可以共同理解，但仍各保留 ID，不允许跨单元搬运台词。长单元不能在任意 token 处截断；只有存在可追溯源边界时才拆成新的子单元，并另存分段版本。
4. 为当前块检索少量前后原文及命中的术语。离线可使用后文消歧，但不得把后文才出现的名字、事实或答案提前补进当前台词。背景和上下文作为不参与覆盖分母的只读资料。

字幕行数不是请求大小的主尺度；完整渲染后的 token 数才是硬预算。合并之前的 cue 映射始终保留，不能用“返回四行”证明原文完整。

## 3. 标题、术语和可选预处理

### 固定资料

- **标题／背景：**只使用用户提供或有可核查来源的片名、场景介绍、人物关系；带来源和版本。标题是背景文字，不存在原生 `title` 字段。尽量简短，不向模型灌输整片剧情来覆盖台词含义。
- **术语表：**记录源词、接受译法、适用范围、来源／审核状态；只注入本块有关条目。称呼和代词不因已知角色姓名就机械替换。存在多种正确译法时保留适用条件，不要求每句出现目标词。
- **局部上下文：**保留原文 ID，前后段分区，明确“不输出”。已接受译文可提供少量表达一致性示例，必须和事实来源区分。

这些资料可独立启用，不要求每次请求填满全部段落。上下文选择可从直接相关邻文开始，对省略主语、指代或敬称歧义扩大范围；固定邻文窗口与按疑点扩展都是待测策略。分别比较标题、背景和已接受句对带来的消歧收益、额外 token 与污染风险，不能只凭输入更多就认定更准确。

### 可选的便宜通用模型预处理

若字幕较长，可用一个已验证且可本地运行的较小通用模型预处理原文：建议语义边界、提取术语候选、生成场景摘要。不要求 Hy-MT2 兼任完整规划器，也不在本提案指定新的模型或下载安装。

预处理输出需要逐项指向源 ID／源跨度。程序校验源范围、顺序、保护边界和覆盖，后续独立审校核查术语并保留未决状态；模型不能修改时间码、补全省略主语或把猜测固化为事实。没有可靠收益时可以关闭此阶段，直接用规则和原文。

`compact` 的对象应是**有来源的场景事实与接受译名**，而非前几批译文的无来源摘要。摘要保留证据 ID、不确定性、版本及当前可用范围；从原文重建，场景切换时重置短期内容。摘要的任务是缩小重复输入，不是让历史错误永久化。默认每块新建请求并重建显式上下文；持续聊天与滚动译文记忆只作为另外的对照实验。

这里的预处理、摘要和收益均为工程提案；官方有背景／术语任务依据，没有核验到本项目这些自动准备步骤的效果。

## 4. 合成请求与响应

以下是自行编写的合成数据，不来自用户字幕，也不是模型实测输出。程序保留的源记录为：

```json
[
  {"id":"s101","text":"このことを知っているのは","start":10.0,"end":11.3},
  {"id":"s102","text":"君だけだ。","start":11.3,"end":12.5},
  {"id":"s103","text":"わかった。凛には言わない。","start":12.8,"end":14.2}
]
```

`s101` 与 `s102` 在本例中无受保护断点，合并为 `u041`；`s103` 是另一个说话人的回应，形成 `u042`。程序映射分别为 `u041 → [s101,s102]`、`u042 → [s103]`；完整源跨度依共同契约保存。两者放在一个请求中，不要求每条源 cue 独立翻译。

下方是多种条件叠加的候选示例，适合在基本协议可用后测试，不是每次必用的固定模板。初试可仅保留任务、输出要求和待译正文，随后按需加入只读段；提示长短与段落顺序均可配对试验。来源哈希、时间绑定和覆盖记账由程序承担，不增加为模型任务。

将所选提示作为单条 `user.content`；`〖…〗`、JSON 键名和 ID 是本提案约定，服务端不能把它们误当成原生条件字段：

```text
〖任务〗
把待译 JSON 中 units 每一项的 text 翻译为简体中文。
每个 ID 代表一个完整语义单元；共同理解这些单元，分别返回对应译文。
保持顶层对象、units 数组、条目顺序、id 值和键名不变，仅改写 text。
不要跨 ID 合并、遗漏或重复台词。不要添加时间码、解释或代码围栏。
保留否定、数字、人名、称呼和对白语气，不补写未出现的情节。
输出一个完整 JSON，背景与前后文不进入输出。

〖只读背景〗
合成短片标题：放学后的约定。
当前场景：两名同学约定保守秘密。仅用于消歧。

〖参考译名〗
凛 → 凛；这是本次接受译名，不要求未提及的句子出现此名字。

〖只读前文〗
s100: これは二人の秘密だ。

〖只读后文〗
s104: じゃあ、帰ろう。

〖待译 JSON〗
{"units":[{"id":"u041","text":"このことを知っているのは君だけだ。"},{"id":"u042","text":"わかった。凛には言わない。"}]}
```

预期的示例响应形状：

```json
{"units":[{"id":"u041","text":"只有你知道这件事。"},{"id":"u042","text":"明白了。我不会告诉凛。"}]}
```

消息接口可表达为 `messages = [{"role": "user", "content": prompt}]`。`id`、`units`、只读段和参考译名是应用定义的数据与指令；当前 demo 实际手工渲染后经 `/tokenize` 将 token IDs 交给 `/completion`。当前 30B 的单条 user 渲染形状为：

```text
<｜hy_begin▁of▁sentence｜><｜reasoning_mode｜>reasoning_effort:no_think<｜hy_User｜>{完整提示}<｜hy_Assistant｜><think></think>
```

服务应用本地模型模板；先检查预渲染结果，确认没有丢失任务段、重复模板或使用默认 ChatML。GGUF 内嵌模板与上游模板是否一致仍需本地检查。

### 单单元纯文本路径

选择每个**合并语义单元**独立请求，仍可携带同样分区的只读上下文与相关译名；也可在多单元路径失败时切换到此模式。任务只要求输出当前单元的译文，不要求生成 JSON 或 ID。程序在发请求前把 `request_id → u041` 固定，返回纯文本「只有你知道这件事。」后生成：

```json
{"unit_id":"u041","source_cue_ids":["s101","s102"],"translation":"只有你知道这件事。"}
```

此对象由程序构造，源 ID 来自不可变映射，不来自模型猜测。调度器可以处理多个独立请求，但这与一个 prompt 内的多单元联合翻译不同；初轮只用单请求，后续再测并发。不能退回逐显示行切碎完整句。

## 5. 返回解析与时间完整性

按所选协议执行结构与内容检查，并保留检查方式和复核状态；只有满足该轮成功条件的结果才可标为 `translated`，语义疑点进入 `needs_review`。自动检查通过不等于人工审定：

1. 服务状态完整，未超时／截断／拒答；保留原始返回和结束原因。JSON 路径做严格解析，拒绝重复对象键、额外非空正文和无法确定的尾部内容；可机械剥除 BOM／首尾空白，但不得猜补缺失括号或根据行序猜 ID。纯文本路径检查是否混入解释或只读资料，不尝试将译文解析为 JSON。
2. 对上述数组协议，顶层和条目形状符合最小协议；本次 ID 集合与输入完全相同、唯一、顺序相同，不出现上下文 ID。数组经校验后转为共同契约的单元 ID 键控结果映射；纯文本路径使用请求前冻结的单元身份。两条路径均由程序查表补回源跨度，再核验不可变源哈希及覆盖。原文重复也用 ID 区分，不用字符串相似度重新匹配。
3. `text` 非空且不是解释性输出；检查占位符／受保护标签、数字和接受译名。假名比例、复制相似度等只产生疑点：中日共用汉字、专名和短句可能合理不变，不能靠“没有假名”证明正确中文。
4. 审查错意、否定、指代、遗漏、幻觉和跨 ID 搬运。结构正确不等于语义归属正确；相邻语义依赖组存在疑点时整体进入复核。

实验语义评估按已采纳的 `sol-high-auto-v1` 执行，不安排人工抽样校准；覆盖跨句否定、重复短句、换说话人、后文揭示和同形人名，并保留自动裁判的不确定性。流程内辅助模型审校与独立实验裁判分开；前者仍须测试误报、漏报、修订引入错误和全部成本，不能把结构检查或裁判一致当作可靠语义验收的证明。

可在固定 llama.cpp 版本上增加 `response_format`／schema 或 grammar，以约束 JSON 语法。schema 必须另外在 prompt 说明，因为运行器不会自动把它作为模型可见任务；不支持的 schema 特性可能被跳过。ID 的唯一性、完整集合和实际台词归属仍由应用验证。[llama.cpp v0.5.0 server](https://github.com/ggml-org/llama.cpp/blob/v0.5.0/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions)、[grammar 限制](https://github.com/ggml-org/llama.cpp/blob/v0.5.0/grammars/README.md#json-schemas--gbnf)，访问日期 2026-10-06。该版本是文档核查对象，不是本机已安装引擎的声明。

如果 ID／结构错误成为主要成本，可试由程序生成本批固定 ID 与数组位置的 GBNF，仅让正文字符串自由生成，不要求首版就实现。上述版本文档标记 `prefixItems` 有问题、`uniqueItems` 不支持；ID `enum` 也不保证唯一性或顺序，应检查转换结果并用错误样例验证约束。ID 键控对象等更简洁格式仍可探索，但需要记录为新协议并定义相应校验，不沿用数组协议的验证结论。grammar 的收益、延迟及对译文的影响均需实测。

模型输入／输出均不含可改写的时间码。翻译层只绑定单元；显示阶段按共同契约使用源锚点，保存完整译文、显示切分和来源关联。示例 `u041` 的整体可信跨度是 10.0–12.5 秒，但这不证明「你」应在 10.0 秒显示。若需内部拆分而只有 cue 级时间，就标记细粒度映射不足，保留有界整体或交给复核；不按中文字数伪造精确时间，不把中文 forced alignment 到日语音频。

### 5.1 可选反思阶段

单单元纯文本和多单元结构保持两条路径均可增加“初译→校验→可选审校→必要修订→再校验→显示”。采用[共同设计第 9.1 节](subtitle-translation-common.md#91-可选反思审校修订与再校验)的 `off`／`on_demand`／`all` 模式。**审校与修订模型均暂不定死：可以复用 Hy-MT2，也可以配置其他模型，两个角色无需绑定同一选择。** Hy-MT2 的翻译／结构保持能力不自动证明审校能力，同模型方案同样需要单独验证。

先将两条初译路径都归一为程序持有的 unit ID、源跨度与译文记录，再向所选审校模型发送原文、初译及版本、必要邻文、相关术语、风险与允许修改的 ID。审校可以覆盖一批或语义依赖组，返回 `keep`／`revise`／`unresolved`、简短问题与源证据；不要求重译全批，不使用参考答案。

若复用 Hy-MT2，审校／后编辑提示另立配方并核对原生包装，不能直接把待审译文拼进普通翻译正文后假定模型会纠错；若配置其他模型，使用该模型已验证的任务接口。审校问题格式不强制沿用初译的 `units` 数组；修订产物由 Adapter 归一到原 unit ID，纯文本修订仍可由程序绑定单元。

修订只处理获准范围，保留未改项、源时间与跨度。建议初试一轮审校、至多一轮必要修订，使用共同总预算；再校验结构、原问题及新错误，保留初稿和未决项，失败不伪装为已完成反思。采用新译文后重做目标映射／显示，重检受影响的术语记忆和缓存。

模型、提示、轮数及审校／修订合并调用与否都可迭代，不成为固定产品门槛。比较时保存关闭／开启的独立配方及初译／最终结果，统计纠错、新错误、误报／漏检和包含模型切换的总耗时；同模型反思与其他模型反思都不能混成 Hy-MT2 裸初译成绩。

## 6. 有界恢复

| 异常 | 恢复动作 |
| --- | --- |
| 模板／目标语言错误 | 修正适配后创建新运行身份；模板错误不靠不断调采样掩盖 |
| 超时／服务临时失败 | 有上限地重试同一请求；OOM 先缩小窗口／并发和释放其他模型，不把认证或配置错误当作字幕过长 |
| 截断、输入或输出超限 | 在单元边界缩批，重新计数，保留必要只读邻文；单单元过长则采用可映射子单元或显式失败 |
| 缺／错／重复 ID，非法 JSON | 整块映射不可信时缩批重译；已确认无歧义的独立结果可保留，失败单元与其语义依赖组一起恢复 |
| 仍无法稳定多 ID 返回 | 逐合并单元纯文本请求，由程序包装并检查；记录协议回退，不能伪称首次成功 |
| 有效中文但错意／串段 | 对依赖组带相关源文复核；修订另存版本，不用仅改某一行造成新的跨句问题 |
| 单单元仍复制原文／拒答／空输出 | 简化冲突条件，有限重试；最终显式失败，保留源内容和原因，不能静默回填原文并计作成功 |

一种初始配方可设为每个请求至多一次同配方重试、一次缩批恢复；缩批后仍失败的单元进入纯文本路径，纯文本至多一次恢复请求。次数与先后次序可按错误类型和实测成本调整，不要求为了走完流程而重复已知无效请求；起始即选纯文本时也无需经过缩批阶段。所有子请求与辅助步骤共享原批总预算，不能因分支增多绕过上限。探索中可修改恢复策略并记录新配方，对照运行则固定该轮策略。每个源单元必须处于成功、待复核或失败状态之一；原始尝试、耗时、token 与恢复成本完整保存。

缓存键至少包括源身份／单元跨度、目标语言、模型文件身份、量化、模板与 prompt 版本、解码参数、只读上下文、背景及术语版本。改变译名或 compact 后不能复用语义条件不同的旧结果。运行日志默认只记 ID、状态与统计；完整提示与译文保存在本地忽略目录。

## 7. 预算与本地运行准备

已有 7B Q8_0、30B-A3B Q3_K_M、官方 Q4_K_M 与新增三款量化均有独立运行身份；当前 APEX-I-Compact 基线的固定窗口质量、四轮性能和正式 30 分钟长跑证据见[四量化报告](../research/2026-10-07-hy30-four-quantization-results.md)，其他版本的证据从[评估入口](../testing/translation-model-evaluation.md)检索。使用路径、revision 和 SHA256 以[资产指南](../guides/local-translation-model-assets.md)及本地 manifest 为准。一次加载一个模型，卸载 STT 与可选预处理模型后再加载翻译模型，防止把权重体积当作全部显存需求。记录实际 GPU 驻留、引擎／构建、模板、KV 配置与峰值显存；不把 APEX 混合量化或 30B Q3 的结果写作标准 Q4 或 BF16。

所有下列数值是**一组待测初始配置，不是长期上限或最优参数**：runtime 总窗口可先用 4096 tokens，单请求；完整渲染输入最多 2150、输出预留 1536、安全余量 410，三者总和不超过窗口，余量不低于共同规则的初试 10%。可先试 1 个合并单元，再试 2／4 个单元的块；后续按长度、质量和显存调整批量、并发与预算分配。达到所选配方的 token 上限必须提前缩块，不承诺任意 4 个单元都可容纳。标题、术语、上下文、JSON 和特殊 token 全计入预算；对实际模型 tokenizer 计数，不按日文字数估算。

不以容纳全片为由直接扩大窗口；需要更多上下文时，可在兼容性、显存与质量验证后调整，超出官方部署边界的实验另行标明。若 4096 也不能满足实际显存／runtime，则缩小配置并记录；运行中不启用隐式 context shift 丢弃源文。优先移除低相关背景与重复只读上下文，保留核心指代证据和完整待译单元；必要上下文无法容纳则标为待复核。

建议以官方推荐值建立第一份解码控制，再按实测调整；每份配方显式记录参数：

| 模型 | temperature | top_p | top_k | repetition_penalty |
| --- | ---: | ---: | ---: | ---: |
| 7B | 0.7 | 0.6 | 20 | 1.05 |
| 30B-A3B | 0.7 | 1.0 | -1 | 1.0 |

表来自[官方部署推荐](https://github.com/Tencent-Hunyuan/Hy-MT2#inference-and-deployment)，访问日期 2026-10-06；输出上限按当前块预算设置。7B 发布的 `generation_config.json` 写 `top_p=0.8`，因此直接默认加载和本表不是同一配方。[发布配置](https://huggingface.co/tencent/Hy-MT2-7B/blob/main/generation_config.json)，访问日期 2026-10-06。低温或确定性解码作为独立对照，不默认解释为更忠实；服务参数名、取值和 repetition penalty 作用范围在选定 backend 上再次核验。

还需记录**后端实际生效的采样链**。核查的 llama.cpp `v0.5.0` CLI 默认 `min_p=0.05`、重复惩罚窗口为 64 tokens，`top_k` 的禁用值为 0，默认 sampler 链把 temperature 放在后面。首轮可显式关闭未选用的 `min_p`，并记录 seed、sampler 顺序、重复惩罚范围、其他过滤／惩罚开关及服务有效配置；上表 30B 的 `-1` 按后端禁用语义适配。CLI 与接口文档部分默认值不同，不能只看请求里填写的四个数值，也不能声称不同后端数值相同就采样等价。后续可测试不同采样链，但需保留配方身份。[llama.cpp 采样参数](https://github.com/ggml-org/llama.cpp/blob/v0.5.0/tools/server/README.md#sampling-params)，访问日期 2026-10-06；这些默认值不代替实际选定版本的核查。

## 8. 验收与未决问题

建议按以下顺序逐步得到可运行结果；这是一条便于定位问题的探索路径，可以根据实际失败提前处理后续问题、跳过无收益增强或回到前一步，不是实施阶段必须逐项完成的流水线：

1. **基本翻译：**合并语义单元、原生模板、纯文本、无额外背景，检查语言、结束状态、输入未截断和程序映射。
2. **请求协议：**尽早比较单单元纯文本与 2／4 单元 JSON，固定单元划分和可用原文信息；纯文本请求也可提供相同邻文，避免将额外上下文收益误归于批量。若暂不需要批量，可先保留纯文本实现。schema／GBNF 按结构错误的实测成本决定是否加入。
3. **局部增强：**在已有可用路径上逐项比较局部上下文、命中术语、标题／背景和已接受句对，关注错意减少与污染增加的取舍；必要时单独比较提示的简化版与完整组合版。
4. **长片增强：**仅在长距离一致性或重复输入成本值得处理时，再探索源文预分析、场景摘要、compact 或滚动记忆，同时计入辅助模型加载、审校和恢复成本。

协议、上下文、grammar 和采样尽量分开比较；必须同时改变时说明无法单独归因。官方 IFMTBench 中 7B 单约束／多约束得分为 89.73／72.67，这是简化条件值得检验的依据，不是缩短提示必然改善质量的证明，也不是本机 JSON 成功率。[技术报告 v1，表 4](https://arxiv.org/html/2605.22064v1#S3.T4)，访问日期 2026-10-06。

是否保留某项增强，以严重错意／遗漏、内容归属、自动修订量及修订引入错误和含失败恢复的总耗时共同判断；不为减少请求数而牺牲质量。开发集可以边实现边调整并保留记录，正式比较前再冻结该轮配方与质量门槛；不根据固定 test 的有利结果反复调参。新配方替代旧推荐时，在本文更新理由及证据入口，旧运行仍保留原身份。

离线合成检查应覆盖：跨 cue 合并仍保存全部跨度、保护边界阻止合并、重复原文用 ID 区分、上下文不计作待译、错／漏／重复 ID、重复 JSON 键、截断、拒答、空正文、标签与转义、缓存版本变化、缩批仍保留相关上下文、源时间逐项不变、最终失败不隐式补原文。这里只定义检查目标，没有新增测试实现。

模型 smoke 再使用[翻译评估入口](../testing/translation-model-evaluation.md)的冻结数据；先 smoke 后固定 test，参考库的文本复核不等于人工音画金标准。按 `V2-replay`、`V2-native-adapted`、`P-flow` 分别记录输入身份和结果，不往原版 v2 窗口追加本流程可选资料。分别报告首次结构成功率、最终成功率、源语义覆盖、严重错意／遗漏、术语命中及误用、上下文污染、串 ID、截断、重试次数、总耗时、token、峰值显存和自动修订量及修订引入错误。显示读速／时间映射单独报告，不用合法 JSON 或 cue 等数替代字幕质量。

待回答的问题包括：本地 GGUF 模板是否一致；固定 Windows 引擎在 RTX 5080 的实际执行；合并单元的最佳大小与并发；Q8／Q3 对多条件遵循的影响；只读上下文是否被译入；多 ID schema 的支持与实际串段率；预处理与 compact 是否值得额外耗时；仅 cue 时间时自由中文语序的显示策略。没有真实推理证据前，本提案不宣布任何路线优胜或可靠。
