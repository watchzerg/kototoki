# 三个本地翻译模型：输入契约、结构输出与字幕适用性

状态：exploratory；一手资料调研与工程建议，未进行本机翻译实验，未采纳模型。  
最后更新：2026-10-05。  
范围：用户指定 Hy-MT2-7B-GGUF、TranslateGemma-12B-IT、Tower-Plus-9B；面向后续本地日语→简体中文字幕翻译。外部来源访问日期均为 2026-10-05；动态文档不是冻结运行版本。本研究不改变当前原语言 STT 里程碑。

三个子 agent 分别核查官方模型卡、模板、配置、论文与推理实现；本报告综合其发现，并复核关键接口差异。详细用法、自然语言模板解释、伪代码与来源分别见：

- [Tower-Plus-9B 详细调研](2026-10-05-tower-plus-9b-local-translation.md)。

**建议先用 Hy-MT2 验证带背景、术语和结构的字幕翻译，用 TranslateGemma 建立遵循原生契约的纯翻译对照，用 Tower+ 验证一般指令模型路线。** 这个顺序依据任务接口和部署条件，不代表日中翻译质量排名。三个模型必须用同一冻结原文和人工审查才能比较实际质量。

## 能力对照

表中“官方支持”指有文档或训练／评测依据，不代表每次生成都符合要求；“待测”指可以设计实验，尚无足以建立可靠契约的证据。

| 关心的问题 | Hy-MT2-7B-GGUF | TranslateGemma-12B-IT | Tower-Plus-9B |
| --- | --- | --- | --- |
| 提示词自由度 | 翻译专用但支持多类自然语言任务指令；仍须使用原生 chat template | 严格结构化翻译入口；不能当作普通聊天 prompt 使用 | 自然语言指令入口；应保留其 Gemma 2 聊天包装 |
| 标题、背景 | 官方有独立背景段示例；标题／简介可放入该段，具体收益待测 | 没有“参考但不翻译”的背景字段；放进 `text` 会被视为待译材料 | 可以作为指令实验；没有核验到专门的背景字段或可靠遵循保证 |
| 术语表 | 官方有源词→目标词参考译法模板 | 无官方 glossary／常规 prompt 强制术语接口 | 论文评价翻译＋附加规则；任意 glossary 的精确命中仍须测 |
| 语气／字幕压缩 | 官方有风格、个性化条件；压缩是否损失含义要单测 | 没有官方风格指令字段 | 可尝试自然语言条件，字幕长度控制未验证 |
| 一次输入多段正文 | 可组合，并有分隔符与结构保持指令；不承诺逐项独立 | 单个 `text` 可有段落；不是多个独立 `content` 项 | 可组合成长文本；未建立稳定段落／ID 对应契约 |
| 多段分别返回 | 最适合试有 ID 的结构化输入，但必须校验漏项和串段 | 推荐分别请求、程序保留 ID；不要依赖模型保留段落边界 | 最稳妥仍是分别请求；一次多段保留 ID 属待测 |
| JSON 输出 | 官方结构化数据翻译范式可用于 JSON；非任意 schema 的硬保证 | 请求对象是结构化的，默认输出仍是译文；无原生 JSON 输出指令契约 | 可要求 JSON，但没有官方严格 schema 输出保证 |
| 上下文应怎样理解 | 官方仓库写 `max_context: 8192`；配置 262144 不能视为已验证窗口 | 官方卡写总输入 2K tokens；不能直接套 Gemma 3 架构容量 | 官方卡写 8192 tokens；输入、模板和输出共享运行预算 |
| 本地文件形态 | 用户给的是官方 GGUF，可直接研究量化运行 | 用户给的是原始权重；量化／转换另记身份 | 用户给的是原始权重；量化／转换另记身份 |

接口依据：[Hy-MT2 官方卡](https://huggingface.co/tencent/Hy-MT2-7B-GGUF)、[官方仓库部署说明](https://github.com/Tencent-Hunyuan/Hy-MT2#inference-and-deployment)、[TranslateGemma 官方卡](https://huggingface.co/google/translategemma-12b-it)、[Google 对提示词和术语的回复](https://huggingface.co/google/translategemma-12b-it/discussions/2)、[Tower+ 官方卡](https://huggingface.co/Unbabel/Tower-Plus-9B)。模板与配置细节见三份专项报告。

## 1. “一次输入多段”有三种含义

**独立批处理：** 每段都是单独请求／序列；推理框架可以同时执行，但段落之间不会因此自动共享上下文。程序知道每个结果属于哪个输入，模型不需要生成编号。三个模型都可在兼容后端上研究这条路线；批大小与 GPU 内存容量需要实测。

**共享上下文的多段翻译：** 同一 prompt 中有几个段落，模型能够利用相邻内容。代价是可能合句、漏句或改变边界；即使保留相同数量的分隔符，也不证明每段内容对应正确。Hy-MT2 的指令接口最直接；Tower+ 属提示词实验；TranslateGemma 的多段正文可作为同一待译文本，不能偷偷把部分正文当成不需要输出的背景。

**多轮历史：** 前面有 user／assistant 译文，不等于独立批处理；历史译错也可能影响后文，且不断消耗窗口。模板能接受多轮，只能证明序列格式成立，不能证明文档翻译质量或术语记忆稳定。

因此，用户要求“每段分开处理”若意味着绝对独立、确定对应，优先使用独立请求；若意味着共同理解但分别返回，就要另外测试多段结构保持。请求批处理与单次生成的区别由推理框架实现决定，可参照 [Transformers pipeline 批处理说明](https://huggingface.co/docs/transformers/main_classes/pipelines#pipeline-batching)；模型级限制见专项报告。

## 2. JSON 应放在哪一层

最简单可靠的基础方案是：**模型输出一个翻译单元的文字，程序生成 JSON，并从原始记录复制 ID、时间和源跨度。** 这样 TranslateGemma 也能为产品提供 JSON 结果，而无需迫使它成为结构化生成模型。

```python
results = []
for unit in translation_units:
    text = translate_with_native_contract(unit.source_text)
    results.append({
        "id": unit.id,
        "source_cue_ids": unit.source_cue_ids,
        "translation": text,
    })
save_json(results)
```

这是建议的程序层伪代码，未实现。`unit` 可以是一个完整话轮并覆盖多个源 cue，不应机械地等同于一条显示字幕；这里也没有声称解决了中文重新分行和时间分配。

若需要一次生成多条译文，可对 Hy-MT2／Tower+ 比较“分隔符”“最小 ID 对象”“JSON schema”三种输出。Hy-MT2 的结构保持范式有更直接的官方依据；Tower+ 的 schema 用法仍需实验。TranslateGemma 强制 JSON 则偏离其受支持的纯翻译契约，应另立非标准实验。

`llama.cpp` 可以把部分 JSON Schema 转成 grammar，但 schema 并不会自动进入 prompt；不支持的 schema 特性还可能被跳过。完整、未截断且运行正常的受约束输出，可获得相应语法约束，不能由此推出语义完整或 ID 内容对应正确。[llama.cpp grammar 文档](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)

至少分开验证以下结果：JSON 可解析、结构符合 schema、ID 唯一且无缺失、每条源文都被正确覆盖、术语符合要求、没有译入背景、没有提前停止。任何一层失败都应记录；只报告最终修复后成功会掩盖真实成本。

## 3. 对字幕最关键的额外特性

以下是结合接口证据提出的实验关注点，不是三模型已测出的优劣：

| 特性 | 为什么影响字幕 | 建议怎样检查 |
| --- | --- | --- |
| 跨 cue 的不完整句 | 日语谓语、否定或宾语可能位于下一条 | 逐 cue 与完整句／话轮配对比较，检查否定和指代 |
| 背景与正文的边界 | 标题／简介可能被译出，或造成提前泄露、添情节 | 只提供有来源的短背景，检查是否污染译文；TranslateGemma 原生路径不加背景段 |
| 人名、敬称与省略主语 | 统一术语不等于应把所有称呼机械替换 | 审核人物关系、语气、姓名译法和自然省略，不强制补无依据主语 |
| 同时满足多个约束 | 保留 ID、格式、术语、短句可能争夺模型能力 | 从纯翻译逐项增加条件，分别统计内容与结构失败 |
| 字幕阅读负担 | 忠实译文也可能过长 | 保留完整译文，单独评价压缩版本的语义损失；显示标准由产品另定 |
| ASR 错字与断句 | 模型可能流畅地“修正”成错误剧情 | 参考原文与 ASR 输出分组比较，保留不确定内容 |
| 量化与采样 | 通用翻译分数不能代替结构遵循表现 | 固定输入、prompt 和运行版本，独立比较精度、采样与重试 |
| 失败恢复 | 整块重译可能使已正确译文改变 | 只重试失败单元或缩批，保留运行身份与全量失败分母 |

Hy-MT2 官方论文另外给出量化后的翻译与指令遵循评测，适合作为“两个维度都要测”的依据；其家族字幕案例不等于本机 7B GGUF 的字幕验收。[Hy-MT2 技术报告](https://arxiv.org/abs/2605.22064) 显示与时间映射的相关一手研究及评估方法见[字幕翻译总报告](2026-10-05-subtitle-translation.md)和[日中字幕质量评估](2026-10-05-translation-evaluation.md)。

## 4. 本地部署与选择次序

**Hy-MT2 优先研究已有／官方 Q8_0 路线。** 官方 GGUF 列有多种精度，符合先保证质量、再比较资源的项目偏好。模型卡的通用命令并不是本机验证结果；其中 STQ 特殊量化说明不能不加区分地套到所有普通 GGUF，`-ngl 0` 也不能作为 GPU 推理示例。需要记录实际文件来源／哈希、模板、引擎版本、GPU offload 和内存峰值。

**TranslateGemma 保留为纯翻译质量对照。** 用原生源／目标语言字段与单个正文输入；产品端包装 JSON。原始 12B 权重、量化后的文件和某个 UI 中的“TranslateGemma”标签是不同身份，不能混记结果。Google 模型受 Gemma 条款约束，模型卡还提示权重访问需接受条款。[官方模型入口](https://huggingface.co/google/translategemma-12b-it)

**Tower+ 保留为灵活指令路线的候选。** 除一般指令训练外，论文 IF-MT 也评价了 9B 的翻译＋附加规则能力；这比“它是聊天模型，所以大概能遵循”更有依据。不过该评测主要是英语→中文／西语，不能直接推成日中 glossary、字幕结构或 JSON 的可靠性结论。[Tower+ 论文](https://aclanthology.org/2026.acl-long.1366.pdf) 模型卡正文与 metadata 的许可标记不一致，二者都带非商业限制；将其列为商业产品默认前需澄清具体授权。本次仅记录官方标记，不作法律解释。[Tower+ 模型卡](https://huggingface.co/Unbabel/Tower-Plus-9B)

三个模型都不应与 ASR／CTC 同驻显存后再假设容量足够。建议初轮按阶段卸载后测试，分别测权重、KV cache、并发数与输入长度。官方 Linux／vLLM 示例不能直接当成原生 Windows 操作指南；本轮没有安装、更换环境或实际 GPU 推理。

## 5. 后续比较应分两轮

第一轮比较**各自原生契约下的翻译质量**：同一组人工检查过的日语完整句／话轮，目标简中，纯文字输出，程序记录对应关系。固定模型 revision、量化、引擎、模板、解码参数与输入来源；共同短输入用于公平对照，长输入另列能力测试。

第二轮比较**字幕工作流能力**：在第一轮基础上，分别增加可靠背景、相关术语、多段结构、输出长度条件。只在支持相应契约的模型上把它们算作标准用法；TranslateGemma 绕过模板的实验应单列，不能因为它不支持 glossary 就直接判定基础翻译能力差。

人工审查至少覆盖：准确度／遗漏、人物与指代、否定和数字、对白语气、自然程度、术语一致、cue 映射、长度和时间适配。另报告格式成功率、截断率、重试率、端到端耗时、峰值显存。多模型自家 benchmark 不同数据／语对／精度下的分数不应拼成总榜。

本轮完成的是公开资料核查与文档整理；三者的本机质量、吞吐、窗口上限、量化损失及 Windows GPU 兼容性仍待实测。README 与 AGENTS.md 的当前 STT 范围仍准确，因此不改写里程碑。
